# ابدأ من هنا — Digital Menu SaaS

الحزمة دي **تسليم مواصفات وتعليمات للـAI Agents**، وليست مشروعًا منفذًا أو نظامًا اختُبر أداؤه بالفعل.

## خطوات التنفيذ
1. أنشئ مستودع GitHub جديدًا وخاصًا في البداية باسم `digital-menu-saas`.
2. فك الحزمة داخل جذر المستودع بحيث يبقى `AGENTS.md` في الجذر، و`docs/` و`prompts/` بجانبه.
3. افتح المستودع داخل Codex أو Antigravity. اطلب من الـAgent قراءة `AGENTS.md` و`docs/` أولًا.
4. انسخ محتوى `prompts/00-plan-only.md` داخل محادثة الـAgent. **دي مهمة تخطيط فقط، ممنوع تعديل الكود فيها.**
5. راجع خطة الـAgent، خصوصًا آلية فصل بيانات المطاعم، حماية الجلسات، رفع الصور، خطة نشر المنيو، واختبارات الأداء.
6. بعد اعتماد الخطة، ابدأ مع Codex بـ`prompts/01-foundation.md` لبناء أساس المشروع. اطلب فرعًا منفصلًا وPull Request وتقرير أوامر البناء والاختبارات.
7. بعد إنشاء أساس يمكن للواجهة الاعتماد عليه، ابدأ مع Antigravity بـ`prompts/05-ui-design.md` لمقترحات التصميم. لا تشغّل Agentين يعدلان نفس الملفات أو نفس الفرع.
8. بعد كل PR، استخدم `prompts/08-review-another-agent.md` لمراجعة مستقلة، ثم لا تعتمد المهمة إلا بعد ظهور دليل تنفيذ الاختبارات.
9. لا تسمح بنشر إنتاجي أو تدمير بيانات أو تشغيل أوامر حساسة إلا بعد مراجعة وموافقة صريحة.

## تقسيم مبدئي
- **Codex:** F01 إلى F09 (Backend وAuth وDatabase وSecurity).
- **Antigravity:** U01 إلى U04 (تصميم وتجربة المستخدم وAngular).
- **مراجعة متبادلة:** Security/Performance/E2E وPR Review.

## ما الذي يجب أن يعيده كل Agent بعد كل مهمة؟
- الملفات التي أنشأها أو عدّلها وأسبابها.
- كيف تحقق من صحة التنفيذ بالضبط، بما فيها أوامر البناء والاختبار ونتيجتها.
- اختبارات اختراق أو وصول مطعم لبيانات آخر إن كانت المهمة تمس قاعدة البيانات.
- نتائج الأداء **المقاسة** وليس صفات مثل «سريع جدًا».
- مشاكل لم تُحل أو اختبارات لم تُنفَّذ مع علامة NOT RUN.
- خطوات التشغيل والتحقق يدويًا وملاحظات تعلم بالعربي.

## إعدادات أمان للـAgents
- في Antigravity على Windows، فضّل وضع طلب مراجعة أو استخدام Sandbox، وتجنب التنفيذ غير المقيد، خصوصًا في البداية.
- في Codex، استخدم حدود عمل مناسبة وموافقة على العمليات الحساسة؛ لا تعطِ أسرار إنتاجية إلا عبر قناة إعدادات آمنة عند الحاجة.
- ممنوع نشر كلمات مرور أو Tokens في الـPrompts أو صور الشاشة أو المستودع.

## قبل إطلاق نسخة للمطاعم
لا تقل «آمن» أو «أداء ممتاز» اعتمادًا على كلام الـAgent: اطلب Test Results، فحص Tenant Isolation، تجربة الـQR على هاتف فعلي، Benchmark على استضافة مشابهة للإنتاج، تجربة استعادة Backup، وخطوة مراجعة بشرية للنشر.

## تغيير إلزامي: SEO وPerformance من أول يوم (v1.1)
- **مهم:** الخطة القديمة كانت تقبل Angular CSR للمنيو وتأجيل SSR. القرار ده اتلغى. لازم يبدأ المشروع بـAngular Hybrid SSR للمنيو العام (المحتوى الحقيقي داخل HTML المرسل من السيرفر)، وPrerender للتسويق، وCSR للوحة الإدارة.
- قبل كتابة الكود، شغّل `prompts/09-seo-performance-first.md` أولًا في Codex، وخلّي Antigravity يراجع الخطة. لازم يتحدد Hosting يدعم Node SSR + .NET API وراء نفس النطاق، ولا نفترض إن استضافة ASP.NET العادية تدعم Node.
- أول PR `F01` لازم يثبت بالـHTTP source (من غير تشغيل JavaScript) وجود اسم مطعم وصنف ووصف للصفحة وcanonical ورمز حالة صحيح، ومعاه Lighthouse CI baseline.
- QR ثابت على `/m/{code}` يحوّل مؤقتًا 302 لرابط SEO الحالي `/r/{slug}`؛ QR لا يتغير عند إعادة التسمية. متستخدمش QR الذي يحيل لسلسلة تحويلات.
- كل مطعم ظاهر لازم يكون له عنوان وSEO metadata وبيانات منظمة صادقة وsitemap، مع منع فهرسة المطاعم المخفية ولوحات الإدارة.
- راجع `docs/12-SEO-STRATEGY.md` و`docs/13-SEO-PERFORMANCE-GATES.md` قبل اعتماد أي Pull Request يلمس المنيو العام.
- ظهور المطعم في Google أو نتائج Core Web Vitals مش مضمون بمجرد استخدام SSR؛ لازم Search Console وقياس فعلي بعد النشر.

## التشغيل الآلي عبر GitHub (الحزمة 1.2)
لو هدفك إن Codex وAntigravity يستقبلوا المهام تلقائيًا من GitHub من غير ما تكتب لهم Prompt لكل خطوة، ابدأ بـ `docs/16-GITHUB-BOOTSTRAP-RUNBOOK.md` ثم `docs/14-AUTONOMOUS-GITHUB-DELIVERY.md`. المهام والعلاقات محفوظة في `automation/tasks.json`. **مهم:** رفع الملفات وحده لا يشغّل الـAgents؛ يلزم GitHub repo وصلاحيات وSecrets وAdapters وتجربة تشغيل آمنة. التعديلات الحساسة والنشر للإنتاج يحتاجان موافقة بشرية.
