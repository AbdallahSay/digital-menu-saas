# UX / UI Design Brief (Arabic-first)

## Product design goals
Fast, legible, low-friction mobile browsing; elegant but not visually heavy. Restaurant branding uses logo, cover and primary color within accessible contrast rules. Visitors never need to create an account or click unnecessary dialogs. Owners should complete routine price editing within a few steps.

## Public menu screen states
1. Initial skeleton/placeholder with reserved image size (not jarring layout shifts).
2. Main: restaurant logo/name, optional cover, language toggle, category chips/list, search field, product cards or rows, localized names/descriptions, EGP prices, optimized photos, optional approved restaurant contact links.
3. Empty restaurant: helpful 'menu being prepared' state.
4. Search no matches: reset search action.
5. Temporarily unavailable/unpublished: friendly screen without exposing internals.
6. Not found/network offline/error: clear message, retry where appropriate.
7. Long lists: sticky categories as useful, virtualize only when measured necessary.

## Admin screens
- `/login`: clean secure login/forgot/reset flow as configured.
- `/admin`: overview with counts (sections/items, public published state), link/QR.
- `/admin/categories`: table/list with reorder and publish status.
- `/admin/items`: search/filter/pagination, add/edit modal or dedicated page, price, photo, visibility, category.
- `/admin/branding`: logo, cover, primary color/preview, restaurant info.
- `/admin/qr`: permanent URL, copy, PNG/SVG export, print-friendly preview.
- `/platform`: platform-admin only, restaurants list, create, suspend and owner onboarding.

## Accessibility & i18n
- Arabic default RTL, English LTR; both text direction and icon directional affordances adapt.
- Arabic required for every category/item, English optional with Arabic fallback.
- Keyboard navigation, focus indicator, screenreader labels, contrast at least WCAG AA where applicable, minimum useful touch target size, alt text appropriate, no information conveyed by color alone.
- Use Arabic-friendly font with a small optimized subset if licensing permits; `font-display: swap`; avoid fetching 4 external font weights.
- Responsive breakpoints verified at 320px, 375px, 768px and desktop; zoom to 200% without clipping.
- Currency formatting uses `Intl` and stable EGP; no client-side floating-point math in business logic.
- Owner preview for unpublished content must be authenticated, not encoded as guessable public URL.

## Visual quality checklist
Consistent spacing scale and typography, aligned cards, natural product imagery, restrained animations, safe empty states, no crowded controls, user-tested readability. Capture screenshots of public menu in both RTL and LTR before acceptance.

## Components to design first
Brand header, category tabs, item card, search box, menu skeleton/error/empty cards, owner list/form layout, image picker/crop preview, QR share panel. Use design tokens; defer complex white-label page builders and heavy icon/UI libraries.

## SEO and first paint constraints
- Restaurant name and first visible menu items must be meaningful semantic SSR HTML; don't hide content behind client-only loaders or interaction.
- One descriptive `<h1>`; structured headings for categories; real text, not images/canvas for product names or prices. Accessible HTML links for relevant navigation, correct `lang` and `dir` server-side.
- Keep above-the-fold design lean: small logo, optional lightweight optimized cover only if tested; never force a large hero image to load before product text.
- Each public page needs unique server-populated `<title>`, meta description, canonical and share metadata; no brand-only title reused across restaurants.
- Use Angular `NgOptimizedImage` and correct `width`/`height`, priority ONLY for genuine above-fold/LCP image, lazy-load lower items, responsive `srcset`/`sizes`; avoid CSS layout shifts and blocking fonts.
- QR route redirects directly to a canonical restaurant URL; printed QR deep-link opened on a real phone and timed from scan.
